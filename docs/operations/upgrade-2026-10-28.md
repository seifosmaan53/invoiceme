# Upgrade order: sync protocol 2, payment state, business dates (2026-10-28)

Owner-run checklist for an existing installation. It assumes the procedure in
[customer-update.md](customer-update.md) (backup, verified restore, schema
review, update bundle). Nothing here has been run on any real installation.

## 1. Before the update

1. Take a backup and prove it restores: `npm run backup:verify-restore`
   (exit 0, or 4 reviewed and accepted). Keep it.
2. Run the read-only integrity report (`npm run integrity:report`) and keep the
   output with the private runbook.
3. Decide the business timezone: set `BUSINESS_TIMEZONE` to an IANA name (for
   example `America/New_York`). If unset, the server's own timezone (`TZ` of
   the process or container, usually UTC in Docker) decides what "today" is.

## 2. Database (server stopped, in this order)

Run each with `psql -v ON_ERROR_STOP=1 --single-transaction -f <file>`. All are
additive and idempotent (safe to run again). Keep `DB_SYNCHRONIZE` unset.

1. `018_add_device_change_change_id.sql`, if not applied yet. It stops with a
   duplicate count if the data needs a person's decision; do not edit data on
   your own.
2. `019_sync_revisions_conflicts.sql`: revision columns, sync history,
   tombstones, conflicts, and the revision and tombstone triggers.
3. `020_payment_events_and_state.sql`: refund and dispute state, provider
   event history.

The new server reads the new columns on every client, invoice, item and
payment query: start it only after 019 and 020. It checks the triggers itself
at startup and refuses sync writes (503) if they are missing; the integrity
report's fingerprint markers are clues, not proof.

## 3. Server

1. Configuration (see `backend/env.example`): `BUSINESS_TIMEZONE`; leave
   `SYNC_LEGACY_WRITE_CUTOFF` unset; `SYNC_RETENTION_DAYS` and
   `SYNC_CONFLICT_RETENTION_DAYS` only if the defaults (400 and 180 days) do
   not fit.
2. Start the new server. Expect, on the first overdue run, every active sent
   invoice past its due date to become `overdue`, with one notification each
   to the account owner (never to clients).
3. Stripe: add `charge.refunded`, `charge.refund.updated` and
   `charge.dispute.*` to the webhook endpoint's events, so refunds and
   disputes appear on invoices. Nothing is reconstructed for refunds or
   disputes from before the update.
4. Optional, after a fresh verified backup: remove `client_secret` values left
   in old payment rows: `npm run payments:scrub-secrets` (dry run), then with
   `--apply --i-have-a-verified-backup`. Backups, dumps and logs taken earlier
   still contain them.

## 4. What changes for people using it

- Older app versions keep syncing (protocol 1), but edits of sent, overdue or
  paid invoices and their items, of deleted records, and of records with an
  open conflict are refused (`client_upgrade_required`, `record_deleted`,
  `open_conflict`), and sync can no longer un-delete. Their writes have no
  concurrency check; this ends only when they update.
- Deleted clients and invoices are no longer returned by id, accepted as
  references, exported or marked overdue.
- API keys created without permissions have no access (since the earlier
  fail-closed change).
- Invoices show payment state (paid, partially refunded, refunded, disputed,
  dispute lost) beside their status; refunds and disputes never reopen an
  invoice; **Reopen** does, explicitly, and online payment then asks only for
  what is still due. Online payment waits while a dispute is open.

## 5. Mobile release (after the server)

The source for the protocol-2 app (conflict screen, payment state, attachment
URL check) is merged; **no app build has been released**. This machine could
only produce a web build, which leaves sync out (sync runs on device builds
only). A release needs an Android or iOS build with a real signing key
(release builds are currently signed with the debug key), tested against the
updated server. A protocol-2 app does not fall back to the old format: with
an older server it keeps its queue and shows that sync needs a server update.

## 6. Later: ending older apps' writes

After a protocol-2 app release is confirmed and installed, set
`SYNC_LEGACY_WRITE_CUTOFF` to a date; recommended 60 days after that release.
From then on older apps keep read access but every push is answered
`client_upgrade_required`. No date is set in this repository.

## Rollback

The previous server version ignores the new columns and tables, so they can
stay. Do not roll back to a version older than the earlier security fixes
(see customer-update.md). A protocol-2 app needs a protocol-2 server: hold the
app release back if the server is rolled back.
